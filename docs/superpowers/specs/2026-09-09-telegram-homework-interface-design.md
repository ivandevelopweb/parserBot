# Telegram-интерфейс домашних заданий

## Решение

Добавить долгоживущий режим `npm run bot`. Он сразу выполняет один sync, затем
запускает следующий sync каждые 10 минут и параллельно получает обновления
Telegram через обычный Bot API long polling. Существующий `npm start` остаётся
smoke-test/debug режимом, а `npm run sync` — одноразовым production sync.

Состояние интерфейса и выполненных заданий хранится в SQLite
`data/homeworks.sqlite` через встроенный `node:sqlite`. Полный API response в
базу не сохраняется: в записи остаются fingerprint, snapshot задания,
идентификаторы, даты, статус и timestamps. JSON `data/state.json` сохраняется
для совместимости существующего одноразового sync; новый `npm run bot` ведёт
свой источник состояния в SQLite.

## Интерфейс

Разрешён только `TELEGRAM_CHAT_ID` из `.env`. Входящие сообщения `/start`,
`/menu`, `/current` и `/completed` показывают inline-клавиатуру:

- `📚 Поточні завдання` — текущие невыполненные задания, сгруппированные по
  `targetDate`; дата выводится в списке, а предмет — отдельной кликабельной
  inline-кнопкой;
- `✅ Все виконані завдання` — задания, помеченные выполненными, также с
  просмотром деталей.
- `ℹ️ Довідка` — подсказка с командами `/start`, `/menu`, `/current`,
  `/completed` и `/help`.

Нажатие на задание показывает его snapshot, а отдельная кнопка
`✅ Позначити виконаним` меняет статус в SQLite. Callback data использует
числовой id записи, а не fingerprint, чтобы оставаться короче лимита Telegram.
Списки разбиваются на страницы, если Telegram message или клавиатура слишком
великие.

Каждое новое задание отправляется отдельным сообщением с заголовком
`📚 Нове завдання`, предметом, описанием, count прикреплённых файлов (если
больше нуля) и кнопкой для завершения. Изменённые description, targetDate или
topics отправляются отдельным сообщением с заголовком об изменении. Успешная
отправка записывается после вызова Bot API; ошибка Telegram не помечает задачу
как отправленную, поэтому следующий sync повторит доставку.

## Sync и идентичность

Sync получает задания существующим `getAppointments()`, использует текущий
dedupe и fingerprint `targetAppointmentId + normalized description`.
Одинаковые фактические задания с несколькими `homeworkId` становятся одной
записью и одним уведомлением. При первом пустом запуске текущие задания
становятся baseline без уведомлений, чтобы не прислать старый архив. Если в
`data/state.json` уже есть baseline, он импортируется в пустую SQLite-базу без
уведомлений.

В каждой итерации сначала все записи отмечаются не текущими, затем текущие
задачи upsert-ятся. Задания, исчезнувшие из API, не удаляются: они скрываются
из списка текущих и остаются доступными в истории выполненных, если были
завершены. Статус выполненного задания сохраняется при обновлении snapshot.

## Надёжность

- Bot API вызовы имеют timeout; long polling использует ограниченный server
  timeout и bounded backoff при сетевой ошибке.
- `429` логируется с `retry_after`; автоматического бесконечного retry нет.
- Один guard не допускает перекрытия двух sync.
- Все новые уведомления отправляются последовательно, по одному на задачу.
- SQLite транзакция атомарно обновляет snapshot/current-флаги; секреты не
  попадают в URL-логи, сообщения ошибок или диагностические логи.

## Проверка

Добавить unit-тесты для SQLite sync, baseline, новой задачи, повторного sync,
изменения, failure доставки, dedupe, callback completion, группировки и
Telegram payload с inline keyboard. После реализации выполнить `npm test`,
одноразовый реальный `npm run sync` и запуск `npm run bot` с ограниченным
smoke-проверочным временем; существующие задания не отправлять как новые при
первом запуске.
