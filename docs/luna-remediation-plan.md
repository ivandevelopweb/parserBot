# План исправления HomeworkParser для Luna

Статус: предложен для проверки пользователем. Передача Luna сопровождающего задания «реализуй этот план» утверждает перечисленные ниже решения; сама подготовка документа ничего не меняет в рабочем приложении.

Основание: `security_best_practices_report.md`, аудит от 2026-09-10. Номера F1–F10 ниже соответствуют номерам findings в отчёте.

Уточнение пользователя: официальный Classroom API заблокирован и недоступен. Текущий путь через браузерные cookies и внутренний web/RPC выбран намеренно и должен остаться. Приоритет — работа существующего личного бота, а не универсальная интеграция. Это уточнение имеет приоритет над рекомендациями отчёта о предпочтительности официального API.

## Цель и выбранный подход

Исправить подтверждённые утечки и ошибки, подготовить приложение к проверке на Render, сохранив одного worker, один чат, SQLite, существующие адаптеры провайдеров и совместимость старых Telegram-кнопок.

Варианты: отдельные локальные заплатки проще, но не устраняют связь обновления списка с ошибкой доставки. Вынос очереди в отдельную БД/сервис существенно расширит проект. Рекомендуемый вариант — транзакционная запись снимка и очередь на существующих полях SQLite; сетевые операции выполняются отдельно после commit.

Разрешённый объём реализации: исходники, тесты, документация и конфигурация деплоя. Реальные аккаунты, работающий бот, личная база, публикация, Git push и деплой в этот объём не входят.

## 0. Зафиксировать исходное состояние

Прочитать AGENTS.md, docs/ARCHITECTURE.md, README.md, package.json, отчёт аудита и затронутые тесты. Проверить наличие Git, не инициализировать его автоматически. Не отменять чужие изменения. Запустить npm test и npm audit --omit=dev; сравнить с исходными 102 проходящими тестами.

Изучить output/audit-probes.mjs. Перенести полезные воспроизведения в обычные test/*.test.js как проверки ЖЕЛАЕМОГО поведения. Скрипт аудита показывает дефекты; его успешное завершение не означает, что они исправлены. Не менять проверки так, чтобы они принимали неправильное поведение.

Вести таблицу: finding → regression test → исправление → проверка → оставшееся ограничение. После каждого этапа обновлять её и запускать релевантные тесты; полный npm test обязателен перед сдачей.

## 1. Закрыть утечки и ошибки конфигурации — F2, F10

Слои: classroom-web.js, classroom-auth.js, при необходимости utils.js и конечные точки логирования.

- JSON.parse ошибок cookie/credential-файлов не должны попадать в публичный текст. Выдавать стабильную ошибку с типом проблемы, без содержимого входной строки.
- Проверять raw Cookie header до Headers.set: запрещённые CR/LF и недопустимые символы должны давать безопасную ошибку. Валидный заголовок сохранять в прежнем формате; не менять семантику успешно работающего cookie-пути.
- Сетевые ошибки с потенциально чувствительными URL преобразовывать в безопасный код/статус, не логировать объект ошибки или цепочку cause целиком.
- В цикле загрузки cookies определить индекс корректно; в ошибке оставить номер записи без cookie имени/значения.
- Проверить не только сообщения исключений, но и полный вывод logger верхнего слоя. Секреты могут проходить через error.message и cause.

Проверки: испорченный JSON, CRLF в raw header, ошибочный домен cookie, испорченные credential/token-файлы, сетевой сбой с чувствительным URL. Использовать уникальные искусственные маркеры и проверять их отсутствие во всём выводе. Старые положительные тесты cookie header и авторизации должны пройти.

## 2. Согласовать runtime — F1

Слои: render.yaml, package.json, package-lock.json только при необходимости, README.md, ARCHITECTURE.md.

- Проверить официальную документацию и выбрать поддерживаемый свежий patch-выпуск Node.js 24 LTS. Не объявлять старый локальный 24.12.0 актуальным только потому, что на нём прошёл аудит.
- Согласовать NODE_VERSION и engines. Обеспечить доступность node:sqlite без экспериментального флага.
- Выполнить import-smoke и тесты на точной версии, указанной для Render.
- Проверить чистую npm ci установку в отдельной временной копии только исходников, тестов и package-файлов. Не копировать .env, Google credentials, cookie-файлы или data/. Не переустанавливать зависимости поверх работающего локального бота.
- Добавить выполнение npm test в проверку сборки Render: допустим buildCommand `npm ci --omit=dev && npm test`, поскольку тесты сейчас не требуют devDependencies. Если это изменится, согласовать команды с реальными зависимостями.

Критерий: чистая установка, import node:sqlite и полный набор тестов проходят на целевой версии; команда сборки не запускает авторизацию и не пишет в личную БД.

## 3. Исправить сопоставление заданий — F3

Слои: homework-db.js, bot-sync.js; E-school parsing/auth не переписывать.

- Сопоставлять весь набор провайдера до изменений БД.
- В первую очередь зарезервировать точные совпадения fingerprint/external id.
- Для оставшихся E-school записей fallback по appointment id разрешён только при ровно одном незанятом старом кандидате и ровно одном незанятом новом задании соответствующего урока. Уже сопоставленную строку нельзя использовать второй раз.
- На чистом baseline разные fingerprints одного урока сохраняются раздельно. Технические дубликаты одного fingerprint дают одну запись.
- Classroom по-прежнему сопоставляется по course-qualified external id, никогда по тексту.
- Сохранять id, статус выполнения и историю уведомлений действительно сопоставленной записи. Не пытаться выдумать потерянные данные, если старая версия уже слила задания.

Проверки: два разных задания одного урока на baseline; тот же набор без изменений; одно изменилось, второе осталось прежним; неоднозначное изменение обоих; новый второй task рядом с существующим; несколько homeworkId одного задания; одинаковый текст в разных Classroom курсах. Проверять не только количество сообщений, но и содержимое обеих записей и устойчивость id.

## 4. Разделить сохранение снимка и доставку — F4

Слои: homework-db.js, bot-sync.js. Это главный архитектурный этап; выполнять после F3.

- Сначала полностью получить и нормализовать ответ провайдера. Ошибка fetch/декодирования не меняет его существующий снимок.
- В одной SQLite-транзакции обновить is_current, записи задач и notification_pending/notification_kind. Никаких await сетевых запросов внутри транзакции.
- При ошибке записи откатить весь снимок этого источника, сохранив прежний текущий список.
- После commit выбирать недоставленные уведомления из БД. Очередь должна включать записи, отсутствующие в следующем ответе провайдера. Отказ нового fetch не должен мешать попытке доставить ранее сохранённую очередь.
- Переиспользовать существующие notification-поля; отдельный брокер/сервер и новая таблица без доказанной необходимости не нужны.
- Успех фиксировать только после успешного Telegram API. Ошибка оставляет запись для следующего цикла. Ошибка одного элемента не должна отменять сохранение снимка и блокировать остальные допустимые отправки.
- При 429 учитывать retry_after: отложить дальнейшую отправку до разрешённого времени, а не проходить всю очередь, вызывая новые 429. Не добавлять бесконечный retry одного запроса.
- До отправки можно объединить несколько несостоявшихся изменений одной задачи в актуальное состояние: несостоявшееся `new` остаётся `new`, для ранее уведомлённой задачи — `changed`. Сохранять полный последний текст в snapshot.
- Сохранить baseline без массовой рассылки, раздельные baseline-маркеры провайдеров и at-least-once семантику. Не обещать exactly-once.
- Не удалять запись с ещё недоставленным уведомлением возрастной очисткой; фильтр completed + age остаётся обязательным.

Проверки: сбой первой доставки при трёх текущих заданиях не скрывает ни одно; исчезнувшая из API запись с pending notification получает повтор; fetch источника упал, но старая очередь доступна; ошибка БД посреди обновления даёт rollback; после reopen SQLite очередь остаётся; успех не дублируется в обычном цикле; 429 не вызывает шквал запросов. Проверить раздельность источников и счётчики успешных/ошибочных действий.

## 5. Нормализовать даты и мигрировать старые значения — F5

Слои: homework-db.js, telegram-bot.js при необходимости.

- Даты на границе БД приводить к валидному UTC ISO через Date.toISOString(), а не String(Date).
- Предусмотреть версионированную, идемпотентную миграцию уже сохранённых completed_at/updated_at, если туда попадали Date.toString()-строки. Сохранить все строки задач и статусы.
- Известные валидные даты преобразовать, неоднозначные/невалидные не удалять и не подменять текущим временем. Безопасно сообщить количество требующих внимания записей без личного текста.
- Не перезаписывать произвольно database_version и не открывать несовместимую будущую версию как старую.
- Не выполнять миграцию на пользовательской БД во время разработки; тестировать созданные временные базы.

Проверки: настоящий обработчик callback передаёт Date → БД → reopen → cleanup; старые текстовые даты мигрируют; ровно 14 дней ещё не удаляются, старше удаляются; pending задачи и недоставленные уведомления сохраняются; повторное открытие мигрированной БД ничего не портит.

## 6. Ограничить размер уведомлений — F7

Слои: messages.js, telegram.js, bot-sync.js.

Рекомендуемое UX-решение: одно сокращённое уведомление, безопасная ссылка на оригинал при наличии, обозначение сокращения и прежняя кнопка выполнения. Полный текст остаётся в SQLite. Разбиение на серию сообщений сейчас не вводить: оно усложняет частичную доставку и восстановление.

Размер рассчитывать по фактически сформированной строке, включая HTML, длинные subject/title/topics, экранированные символы и URL. Не резать готовую HTML-разметку посередине тега или сущности. Если ссылка сама не помещается, использовать проверенный короткий provider URL при наличии или убрать ссылку, сохранив уведомление и кнопку. Не конструировать выдуманные ссылки.

Проверки: 5000+ символов описания, длинные другие поля, много &/<, emoji, длинный URL; строка проходит существующий транспортный лимит, HTML корректен, полный snapshot сохранён, следующее обычное задание также доставляется.

## 7. Тайм-ауты, запуск и завершение — F6, F8

Слои: telegram.js, classroom-web.js, bot-cli.js, sync-cli.js, telegram-bot.js, bot-sync.js, render.yaml.

- Объединить shutdown signal и timeout signal; явный сигнал не отменяет deadline.
- Для Classroom HTTP сохранить timeout до завершения чтения тела. Публичный контракт request/Response менять только вместе с его потребителями и тестами.
- Сохранить существующие ограничения пагинации web/RPC. Исправление timeout в неиспользуемом официальном Google SDK из F6 отложено: не подключать и не дорабатывать этот путь в рамках данной задачи.
- Первичную E-school авторизацию включить в защищённый путь источника. Использовать существующий auth-client, не дублировать login/recovery. Падение E-school не блокирует Classroom и доступ к уже сохранённому Telegram UI.
- При старте polling и scheduler не должны ждать неограниченно долгую initial sync. Immediate sync сохранить, перекрытие циклов запретить.
- Остановка до/во время startup не должна сбрасываться внутри start() и повторно оживлять процесс. Не запускать новые циклы/таймеры после запроса остановки.
- Задать явный бюджет graceful shutdown, прерывать незавершённые HTTP-операции и сохранять очередь для следующего запуска. SQLite закрывать после завершения работы с БД.
- Согласовать бюджет приложения с актуальным Render maxShutdownDelaySeconds по официальной документации. Не считать одно увеличение Render delay исправлением зависания.

Проверки: зависание до заголовков и после них, внешняя отмена и timeout одновременно, E-school login падает при работающем Classroom web/RPC, UI доступен при долгом fetch, запрет overlap, SIGTERM/stop во время startup и sync, отсутствие обращения к закрытой БД. Сигналы и CLI lifecycle проверять на изолированном процессе/подставных клиентах без .env.

## 8. Сохранить рабочий Classroom web/RPC и исправить его сбои — F9

Слои: classroom-web.js, classroom-provider.js, соответствующие тесты и документация.

- Оставить браузерные cookies и существующий внутренний RPC. Не переходить на официальный API, не добавлять OAuth fallback при ошибке web-сессии и не требовать доступа администратора. Уже существующий неиспользуемый официальный адаптер не удалять и не рефакторить без необходимости.
- Не менять работающие RPC ids, opaque mask, маршруты, семантику Cookie header и подтверждённые wire-shapes ради «правильной архитектуры». Любое изменение этой части должно исправлять конкретный воспроизведённый сбой и сохранять положительные сценарии.

- При подтверждённом отказе session/bootstrap один раз инвалидировать кэш и перечитать страницы через текущую cookie jar, затем максимум один раз повторить допустимый запрос. Не обновлять bootstrap на любые 429/5xx и не начинать бесконечные циклы.
- Если cookies истекли, вернуть понятный безопасный статус reauthentication required; E-school продолжает работу. Не реализовывать Google username/password login и не менять OAuth-политику администратора.
- Не трактовать неизвестную структуру RPC как подтверждённо пустой каталог. Для необъяснимого формата выдавать ошибку и сохранять предыдущий снимок; явно валидную пустую коллекцию разрешать. Проверки не должны отвергать уже поддерживаемые wire-shapes или дополнительные неизвестные поля рядом с распознанными данными.
- Не выдумывать новые значения opaque mask, индексов, маршрутов или fixture-задания ради прохождения тестов. Существующую route-dependent выборку нельзя объявлять полной без подтверждения.
- Оставить текущие school/student id и Classroom cutoff. Перенос этих констант в настройки и поддержка других аккаунтов исключены из обязательных исправлений: для работы данного личного бота они не нужны. Не переносить секретные значения в документацию или примеры.
- Не менять период E-school с текущей недели и не вводить автоматический ежегодный сдвиг cutoff: это отдельная продуктовая политика.

Проверки: однократный refresh и успешный повтор, повторный отказ без цикла, expired cookies не выключают второй источник, изменённая schema сохраняет предыдущие данные, валидный пустой ответ, поддерживаемые wire-shapes и дополнительные поля по-прежнему принимаются. Ни отказ web/RPC, ни истечение cookies не вызывают перехода на OAuth/API.

Полнота Classroom остаётся отдельной проверкой текущего web/RPC-пути: зафиксировать шаги сравнения видимых заданий UI и нормализованной выборки на нескольких курсах/страницах. Без прямого разрешения не запускать live smoke. Если подтверждён пропуск нужного задания, исследовать существующий web/RPC-путь, а не предлагать недоступный официальный API. Не обозначать полноту «исправленной» одними mock-тестами; непроверенная полнота не повод отключать рабочую интеграцию.

## 9. Итоговая проверка и передача

- npm test на целевой версии; npm audit --omit=dev; чистая сборка без секретов.
- Проверить Render Blueprint по актуальной официальной схеме/документации: один worker, постоянный /var/data, секреты без значений в YAML, правильная startCommand и shutdown budget.
- Проверить diff/список изменённых файлов. Если Git появился, проверить отслеживаемые приватные файлы; не полагаться только на ignore. Если Git отсутствует, явно сказать, что историю проверить нельзя.
- Обновить README и ARCHITECTURE: двухфазный sync, очередь, миграция, сокращение сообщений, конфигурация, тайм-ауты, shutdown и реальные пределы Classroom.
- Отчёт аудита сохранить как историческое основание. Итог реализации записать отдельно, например docs/remediation-results.md: F1–F10, тесты, результаты, частично закрытые пункты и причины.
- Подготовить операторский checklist будущего переноса: остановить старый polling, согласованно сохранить/перенести SQLite при необходимости, задать секреты Render, запустить один worker, проверить источники/доставку/перезапуск. Самому эти внешние действия не выполнять.

## Критерий завершения

Все воспроизводимые локально дефекты используемых production-путей закрыты проверками желаемого поведения, существующие контракты сохранены, тесты проходят на runtime Render, секреты не появляются в ошибках, данные не теряются при частичной неудаче, очередь переживает restart. Неиспользуемый официальный Classroom API и универсализация конфигурации исключены из объёма; относящиеся к ним замечания отметить как отложенные, а не исправленные. Live-готовность и полнота Classroom должны быть подтверждены отдельно либо явно оставаться непроверенными. Честный статус «локальные исправления готовы, live-проверка ожидается» предпочтительнее необоснованного «готово к production».
