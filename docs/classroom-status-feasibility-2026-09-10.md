# Проверка статуса сдачи Classroom через cookies

Дата: 10 сентября 2026. Цель — проверить возможность чтения статуса сдачи без официального API. Это исследование; рабочий код не изменён.

## Вывод

Чтение разделов невыполненных и выполненных работ через текущую cookie-сессию подтверждено реальными ответами Google. Для синхронизации можно использовать явную принадлежность задания к запрошенному набору состояний, сопоставляя courseId + assignmentId. Исчезновение из одного списка само по себе подтверждением выполнения не является.

Обнаружена ошибка действующего запроса: `COURSE_WORK_SORT_FIELDS` в `src/classroom-web.js:54` содержит состояния раздела `turned-in`, а не поля сортировки. Эти значения используются в `createCourseWorkRpcPayload` в позиции `payload[2][0][14]`. Поэтому действующий парсер запрашивает сданные/возвращённые/оценённые работы и сохраняет их в боте как pending, если пользователь не отметил их вручную.

## Независимые подтверждения смысла параметра

1. HTML, полученный с cookies по `/a/not-turned-in/all`, содержит `data-display-state-v2s="1,2"` у основной модели списка.
2. HTML `/a/turned-in/all` содержит `data-display-state-v2s="3,4,8,10,5,7,9,6,11"`. Это точное совпадение с текущей константой запроса.
3. Публичный JavaScript-модуль Google `esv3Ef` читает `displayStateV2s` из атрибута модели. Метод `uod(a,b)` записывает этот набор в protobuf-поле 15 (`Bj(a,15,b)`), которое соответствует индексу 14 в массиве фильтра существующего RPC-запроса.
4. В том же модуле `pONvgf` определён как `/HomeroomDataService.QueryStreamItem`, запрос чтения.
5. Публичный веб-клиент различает `done`, `not-done`, `returned` и содержит украинские подписи «Здано», «Призначено», «Повернено». Раздел `turned-in` шире простой пары состояний сдачи; политику возврата учителем нужно определить отдельно.

Проверялась версия публичного ClassroomUi `uk.nrgF6wX3DXQ.2018.O`. Копии публичных JS-модулей сохранены только в игнорируемой Git папке `output/`. Полные авторизованные HTML/RPC-ответы и cookies на диск не сохранялись.

## Живое сравнение

Для каждого из 22 обнаруженных курсов использован один и тот же существующий клиент, декодер и механизм пагинации. Менялся только массив состояний в запросе. Первое поле запроса оставлено равным 100.

| Запрос | Всего работ | После существующего фильтра updatedAt от 01.09.2026 |
| --- | ---: | ---: |
| Текущий запрос, состояния раздела turned-in | 847 | 9 |
| Состояния раздела not-turned-in, `[1,2]` | 50 | 11 |

Пересечение идентификаторов между двумя выборками — 0. В одном небольшом курсе дополнительный запрос с объединённым набором состояний вернул ровно объединение двух выборок: 1 + 1 = 2. Это не доказательство полноты во всех курсах.

Повторный полный прогон дал 850 работ текущего фильтра (12 после cutoff) и 48 невыполненных (9 после cutoff), снова без пересечения. Причина изменения итогов между прогонами не установлена; нельзя без доказательств приписывать её действиям пользователя или считать выдачу стабильной.

### Ограничение полноты, подтверждённое повторно

В большом курсе объединённый фильтр состояний вернул 189 работ на двух страницах. Отдельные фильтры вернули 185 + 2 = 187 работ. Две записи встречаются только при объединённом запросе.

В дополнительном изолированном эксперименте выполнена последовательность «все → невыполненные → выполненные → все». Оба общих запроса вернули один и тот же набор из 189 идентификаторов; отдельные выборки снова дали 187, без пересечения и без лишних записей. Это расхождение не объясняется добавлением/удалением записей общего списка во время этого эксперимента. Его причина (семантика фильтра, особые записи или пагинация внутреннего RPC) пока не установлена.

Таким образом, получение явных выборок состояний подтверждено, но полнота классификации всех работ не доказана. Перед production-интеграцией нужны проверка этих двух записей и политика unknown, сохраняющая прежний статус.

Количество 11 относится к существующему фильтру по дате изменения в первом прогоне, а не ко всем незавершённым работам пользователя. В первом прогоне фильтр невыполненных вернул 50 работ.

## Что можно реализовать

- Получать явные выборки невыполненных и выполненных через cookies с ограниченной пагинацией.
- При подтверждённом переходе того же идентификатора в выполненные обновлять статус в Neon.
- При отмене сдачи восстанавливать только автоматически выполненные задачи, сохраняя выбранный приоритет ручных отметок Telegram.
- Не менять статус при ошибке, неизвестной схеме или простом отсутствии задания в ответе.

Перед реализацией нужно решить политику для работ, возвращённых учителем, для ручных отметок и для исправления уже импортированных 9 записей. Изменение существующего фильтра без политики первого импорта может отправить 11 ранее не импортированных задач как новые. Такой импорт необходимо согласовать отдельно.

Практическая доступность чтения подтверждена. Надёжная полная синхронизация ещё не реализована и не проверена. Действие «сдать → отменить сдачу» на реальном задании не выполнялось: проверка не меняла учебные данные. Не подтверждена долговременная стабильность внутреннего RPC Google.

## Воспроизведение и границы

Локальный исследовательский скрипт: `output/classroom-status-probe.mjs`, запуск из корня проекта через `node output/classroom-status-probe.mjs`.

Скрипт загружает локальное окружение без его вывода, читает фильтры из HTML Google, получает обе выборки и сравнивает их идентификаторы в памяти. В выводе только агрегаты и публичные числовые состояния; отсутствуют имена, тексты заданий, идентификаторы аккаунта и секреты. Дополнительно проверяет объединённую выборку самого большого курса с пагинацией.

Telegram и Neon в этой проверке не вызывались. Работы не сдавались и не отменялись. Рабочие файлы приложения не менялись, коммит и push не выполнялись.
