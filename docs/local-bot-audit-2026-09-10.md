## Куда уходят данные

- `eschool-ua.com`: учётные данные E-school и сессия входа.
- `diary.eschool-ua.com`: сессия дневника и запросы расписания/заданий.
- `classroom.google.com`: экспортированный Cookie header и запросы внутреннего web/RPC. Официальный Classroom API в рабочей цепочке не используется: `src/classroom-provider.js:243`.
- `api.telegram.org`: токен бота и сообщения в настроенный чат. Команды и callbacks проверяют ID чата: `src/telegram-bot.js:46`, `src/telegram-bot.js:189`, `src/telegram-bot.js:226`.
- **Neon:** тексты и метаданные заданий, статусы выполнения, снимки для сравнения и очередь доставки. База облачная, поэтому хранение не ограничено компьютером пользователя: `src/postgres-homework-db.js:199`.

В наблюдавшихся HTTP-запросах были только четыре перечисленных HTTP-хоста. PostgreSQL проверен отдельно. Токены, пароли, cookies, строка подключения, имена курсов и тексты реальных заданий в этот отчёт не включены.

HTML-текст экранируется, ссылки проверяются на HTTP(S) и отсутствие логина/пароля: `src/messages.js:30`, `src/messages.js:38`. SQL использует параметры. По модели задач в PostgreSQL не записываются учётные данные и полные ответы Classroom. Debug smoke-команда может сохранять сырые ответы с учебными данными локально; Git игнорирует такие файлы, но они остаются чувствительными.

Git-проверка не является полным сканированием всех старых значений секретов во всех исторических blob-объектах или удалённом репозитории.

## Замечания

### 1. Средний эксплуатационный приоритет: локальное окружение не соответствует требуемой версии

Доказательство: `test/runtime.test.js:5` падает с `expected Node 24.21+, got 24.12.0`. Остальные 137 тестов прошли, включая новые/изменённые задания, дедупликацию, повторную доставку, изоляцию источников, ограничения доступа и завершение процесса.

Нужно обновить Node до поддерживаемого проектом 24.x не ниже 24.21.0 и повторить `npm test`. Версия 24.21.0 опубликована в [официальных релизах Node.js](https://nodejs.org/en/blog/release/v24.21.0). Установку или глобальные настройки эта проверка не меняла.

### 2. Низкий приоритет безопасности: Cookie header допускается при перенаправлении на HTTP того же хоста

Место: `src/classroom-web.js:1578`, `src/classroom-web.js:1623`.

`headersWithRawCookie` проверяет только `hostname === 'classroom.google.com'`, но не HTTPS и порт. Обработчик перенаправления принимает новый URL без запрета понижения HTTPS → HTTP.

Воспроизведено без сети и реальных секретов: подставной ответ 302 с `Location: http://classroom.google.com/a/not-turned-in/all` привёл ко второму запросу с синтетическим Cookie header по HTTP.

Это условный путь утечки при таком ответе доверенного HTTPS-сервера, а не обнаруженная передача настоящих cookies по HTTP. В реальной проверке такой редирект не наблюдался. Рекомендация для отдельного исправления: запрещать понижение HTTPS и добавлять сырой Cookie header только для точного `https://classroom.google.com` origin; закрепить это регрессионным тестом.

### 3. Средний приоритет надёжности: неподдерживаемая схема Classroom может выглядеть как отсутствие заданий

Место: `src/classroom-web.js:1421`, `src/classroom-provider.js:172`, `src/bot-sync.js:313`.

Декодер возвращает массив распознанных заданий без обязательного различения «ответ действительно пуст» и «схема больше не распознаётся». Успешный HTTP 200 сам по себе не доказывает, что все задания разобраны. Если Google изменит внутренний RPC, источник может вернуть пустой/неполный снимок: новые задания не попадут в уведомления, а прежние могут исчезнуть из текущего списка, оставаясь в базе.

Сегодня адаптер вернул 9 заданий. Рекомендация для отдельного изменения поведения: проверять узнаваемую структуру ответа и при неизвестной схеме сохранять предыдущий снимок, сообщая об ошибке источника. Это требует согласования дизайна по AGENTS.md.

## Как появляются уведомления

1. `npm run bot` подключает Telegram и PostgreSQL, запускает первый сбор, затем повторяет его каждые 10 минут: `src/telegram-bot.js:12`, `src/telegram-bot.js:501`.
2. E-school читает текущую неделю по Киеву. Classroom читает курсы и задания через cookies и внутренний RPC. Неисправность одного источника не мешает попытке другого.
3. Classroom импортирует задания с `updatedAt` начиная с 1 сентября 2026, 00:00 по Киеву; записи без этого времени отбрасываются: `src/classroom-provider.js:18`, `src/classroom-provider.js:62`. Это время изменения, поэтому старое задание после редактирования тоже может впервые попасть в импорт.
4. Первый успешный сбор каждого источника становится baseline без массовой рассылки архива. В текущей Neon-базе оба baseline уже существуют.
5. Новый идентификатор приводит к сообщению **«📚 Нове завдання»**; изменение сравниваемого содержимого — к **«✏️ Завдання змінено»**: `src/messages.js:318`, `src/messages.js:322`. Под сообщением — кнопка выполнения.
6. Сначала транзакция сохраняет снимок и очередь в PostgreSQL, затем выполняется отправка в Telegram. Успех фиксируется только после положительного ответа Bot API: `src/bot-sync.js:171`.
7. При ошибке уведомление остаётся в очереди для следующего цикла. Возможен повтор после аварии между успешной отправкой и записью результата в базу. Уведомления не мгновенные: в нормальных условиях задержка до следующего десятиминутного цикла плюс время сбора.

Команды `/current` и `/completed` показывают задания из базы. Кнопка выполнения меняет статус в базе бота; она не отправляет работу учителю и не помечает её сданной в Classroom. Завершённые задания удаляются спустя 14 дней после выполнения, незавершённые по возрасту не удаляются.

Истёкшие Google cookies требуют нового экспорта: полноценного автоматического входа Google здесь нет. Выключение компьютера, сон или остановка процесса прекращают локальные проверки.

## Действия и границы проверки

Выполнены реальные вход и чтение E-school, чтение Classroom через cookies, три безопасных метода Telegram Bot API и SELECT-запросы PostgreSQL внутри `BEGIN READ ONLY` с последующим `ROLLBACK`. Реальная синхронизация, отправка сообщений, long polling, изменения webhook, запись заданий в Neon и запуск/остановка бота не выполнялись. Запрос `getUpdates` не выполнялся, очередь входящих обновлений не потреблялась.

Проверка зависимостей обратилась к npm registry. Проверка редиректа использовала только подставной transport и вымышленные cookies. Код и конфигурация приложения не менялись; добавлен только этот отчёт. Старый `security_best_practices_report.md` сохранён как исторический документ и не использован как доказательство текущих неисправностей.
