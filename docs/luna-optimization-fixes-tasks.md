## F1. Возобновить уведомления об изменениях вручную восстановленных заданий

Приоритет: высокий. Слои: PostgreSQL persistence, очередь уведомлений, тесты bot-sync. Основное место — `updateObservedTaskWithExecutor` в `src/postgres-homework-db.js`, условие постановки `notificationPending`.

Сценарий: baseline → completeTask → uncompleteTask → провайдер меняет текст или срок. Сейчас новый snapshot сохраняется, но сообщение не ставится в очередь, поскольку после восстановления `completionOrigin` остаётся `manual`.

Согласованное поведение:

- [x] Разделить защиту ручного статуса и постановку уведомления. Для текущего итогового статуса `pending` разрешить обычное уведомление о значимом изменении независимо от ручного происхождения статуса.
- [x] Сохранить `completionOrigin = manual`: провайдер не должен отменять ручное завершение или восстановление. Не удалять все проверки manual и SQL-защиту от конкурентных действий.
- [x] Для итогового `completed` не отправлять уведомления, stale-очередь очищать по существующему контракту.
- [x] Сохранить accounting cutoff, quiet baseline/reconciliation, идентичность задач, отсутствие уведомлений при неизменном снимке и техническом изменении Classroom updatedAt.
- [x] Snapshot и решение об очереди по-прежнему сохранять одной транзакцией; успех доставки фиксировать только после успешного ответа Telegram.

Регрессионные тесты рядом с контрактом:

- [x] E-school и Classroom: после ручного восстановления изменение создаёт ровно одно сообщение; id сохраняется, статус pending/manual, очередь после успеха пуста.
- [x] Повтор того же снимка не создаёт вторую отправку; само восстановление без изменения содержимого не создаёт уведомление.
- [x] Для такого задания ошибка Telegram оставляет очередь pending; следующий sync повторяет доставку, успешный повтор очищает очередь.
- [x] Вручную завершённое задание остаётся completed/manual при изменении содержимого, сообщение не отправляется.
- [x] Ручное действие между matching и persistence сохраняет приоритет; изменение содержимого не теряется. Убедиться, что существующая проверка этого сценария продолжает проходить.

Не восстанавливать пропущенные исторические уведомления автоматически: обновлённый snapshot уже сохранён, и прежний текст может быть недоступен. Не очищать last_notified_at, baseline или всю очередь ради повторной рассылки. В отчёте явно указать, что исправление относится к будущим изменениям.
