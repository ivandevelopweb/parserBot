# Аудит безопасности, корректности и готовности к Render

Дата: 10 сентября 2026 года. Объект: локальная копия HomeworkParser.

**Вердикт: к надёжному деплою пока не готов.** Реальная обработка ответов, SQLite и Telegram реализованы; проект не является демонстрацией с заранее подставленными заданиями. Однако воспроизведены утечки секретов через ошибки, потеря различий между заданиями, проблемы доставки и очистки. Текущая версия Node.js в Render Blueprint не запускает SQLite с указанной командой.

## Высокий приоритет — исправить до деплоя

### 1. [P1] Render закрепляет несовместимый режим запуска Node.js

Места: [render.yaml:10](/C:/projects/HomeworkParser/render.yaml:10), [homework-db.js:8](/C:/projects/HomeworkParser/src/homework-db.js:8), [package.json](/C:/projects/HomeworkParser/package.json).

Blueprint задаёт Node.js 22.5.0, а `npm run bot` не добавляет `--experimental-sqlite`. На этой версии импорт встроенной SQLite без флага завершается ошибкой ещё при загрузке модулей. Локальные зелёные тесты запускались на 24.12.0, поэтому проблему не обнаружили.

Воспроизведение: отдельный Node.js 22.5.0 вернул `ERR_UNKNOWN_BUILTIN_MODULE`; тот же импорт с экспериментальным флагом прошёл. Для воспроизведения не запускался bot-cli.

Исправление: выбрать актуальный исправленный выпуск поддерживаемой LTS-ветки, согласовать `engines`, Blueprint и документацию, выполнить тесты именно на целевой версии. SQLite перестала требовать флаг начиная с 22.13.0, но один этот минимальный номер не заменяет выбор свежего patch-выпуска. [Документация Node.js](https://nodejs.org/api/sqlite.html).

### 2. [P1] Некорректные cookies могут попасть в логи

Места: [classroom-web.js:148](/C:/projects/HomeworkParser/src/classroom-web.js:148), [classroom-web.js:1515](/C:/projects/HomeworkParser/src/classroom-web.js:1515), [bot-sync.js:352](/C:/projects/HomeworkParser/src/bot-sync.js:352). Аналогичная передача ошибки JSON.parse есть в [classroom-auth.js:56](/C:/projects/HomeworkParser/src/classroom-auth.js:56).

Ошибка JSON.parse может содержать фрагмент исходной строки. Код добавляет её `message` в публичную ошибку. Ещё опаснее raw Cookie header: при переводе строки внутри значения `Headers.set()` выдаёт TypeError с содержимым заголовка. Верхний слой логирует эту ошибку без очистки. Такой перевод строки может появиться при копировании секрета в настройки сервиса.

Воспроизведение: искусственный секрет обнаружился в сообщении ошибки и для невалидного cookie JSON, и для raw Cookie header с CRLF. Для второго сценария сетевой клиент не был вызван вообще. Это подтверждённый путь утечки в логи, а не доказательство уже состоявшейся утечки ваших cookies.

Исправление: выдавать стабильные ошибки без исходных значений и без текста исключения парсера/Headers; проверять запрещённые символы до создания заголовка. Добавить тесты на JSON, CRLF и ошибки credential-файлов. Если такие ошибки ранее попадали в реальные логи, соответствующую сессию следует отозвать и секрет заменить.

### 3. [P1] Разные задания одного урока сливаются в одну запись

Места: [homework-db.js:338](/C:/projects/HomeworkParser/src/homework-db.js:338), [homework-db.js:356](/C:/projects/HomeworkParser/src/homework-db.js:356), [homework-db.js:384](/C:/projects/HomeworkParser/src/homework-db.js:384).

Fallback по appointment id считает совпадение безопасным, если в БД ровно один кандидат. Он не учитывает, что во входном наборе одновременно присутствуют два разных задания этого урока. В baseline второе задание пропускается; при обычной синхронизации одна строка перезаписывается попеременно разными заданиями.

Воспроизведение: два задания с одним appointment id и разными описаниями дали **1 строку** baseline. Две последующие синхронизации неизменного набора отправили **3 лишних уведомления**, а в БД по-прежнему осталась **1 строка**.

Исправление: сопоставлять полный набор до записи; применять fallback только при однозначности как старой, так и новой стороны. На первом baseline сохранять разные fingerprints отдельно. Проверить сценарии нескольких домашних заданий к одному уроку и изменения одного из них.

### 4. [P1] Ошибка отправки оставляет текущий список частично скрытым

Места: [bot-sync.js:173](/C:/projects/HomeworkParser/src/bot-sync.js:173), [bot-sync.js:183](/C:/projects/HomeworkParser/src/bot-sync.js:183), [bot-sync.js:224](/C:/projects/HomeworkParser/src/bot-sync.js:224).

Сначала весь источник помечается `is_current=0`. Далее каждое задание сохраняется и немедленно отправляется. Если первая отправка падает, цикл прекращается до обновления остальных заданий. SQLite не удаляет их, но текущий интерфейс их скрывает.

Воспроизведение: после ошибки первого сообщения в БД было **3 задания**, а в текущем списке — **1**. Если недоставленное задание затем исчезает из ответа провайдера, его `notification_pending` остаётся, но доставка больше не пробуется: обработка перебирает только свежий ответ, а не очередь недоставленных записей.

Исправление: сначала атомарно сохранить полный снимок источника и очередь уведомлений, затем отправлять. Обрабатывать сохранённую очередь независимо от присутствия задания в следующем ответе; сохранять правило отметки успеха только после успешного Bot API.

## Средний приоритет — корректность и работа 24/7

### 5. [P2] Очистка выполненных через 14 дней не работает для Telegram callbacks

Места: [telegram-bot.js:289](/C:/projects/HomeworkParser/src/telegram-bot.js:289), [homework-db.js:497](/C:/projects/HomeworkParser/src/homework-db.js:497), [homework-db.js:294](/C:/projects/HomeworkParser/src/homework-db.js:294).

Бот передаёт в `completeTask` объект Date. База сохраняет `String(timestamp)`, то есть строку вида `Sat Aug ...`. Очистка сравнивает её с ISO-датой как текст. Поэтому выполненные через интерфейс задания не удаляются по заявленному сроку; приватные данные сохраняются дольше обещанного.

Воспроизведение через настоящий обработчик callback с подставным Telegram: выполнение 1 августа не было удалено при cutoff 27 августа (**удалено 0**), а сохранённая дата не была ISO. Имеющиеся тесты очистки передают строковые даты и обходят проблему.

Исправление: нормализовать даты в ISO на границе БД и предусмотреть преобразование уже сохранённых строк. Повторить тест полного пути callback → БД → cleanup.

### 6. [P2] Тайм-ауты не охватывают реальные режимы ожидания

Места: [telegram.js:68](/C:/projects/HomeworkParser/src/telegram.js:68), [telegram-bot.js:402](/C:/projects/HomeworkParser/src/telegram-bot.js:402), [classroom-web.js:1475](/C:/projects/HomeworkParser/src/classroom-web.js:1475), [classroom.js:126](/C:/projects/HomeworkParser/src/classroom.js:126).

- Telegram: переданный сигнал остановки **заменяет** AbortSignal.timeout. Бот всегда передаёт такой сигнал в polling. В воспроизведении он оставался активным после рассчитанного клиентского deadline. Ответ сервера с poll timeout не является ограничением зависшего сетевого запроса.
- Classroom web: таймер снимается сразу после получения Response, до завершения `response.text()`. Медленный или зависший body выходит за пределы 30-секундной гарантии. В воспроизведении сигнал уже не прерывался после deadline.
- Classroom official: `timeout` передаётся как API params, а не HTTP request options. Проверка с настоящим googleapis и подставным `auth.request` показала: `options.timeout` не задан, `options.params.timeout` задан. [Официальные request options](https://github.com/googleapis/google-api-nodejs-client#request-options).

Исправление: объединить timeout и shutdown signals; держать deadline до чтения тела; передавать options вторым аргументом Google SDK. Тестировать отдельно зависание до заголовков и после них.

### 7. [P2] Одно длинное задание блокирует последующие уведомления источника

Места: [messages.js:126](/C:/projects/HomeworkParser/src/messages.js:126), [telegram.js:23](/C:/projects/HomeworkParser/src/telegram.js:23), [bot-sync.js:224](/C:/projects/HomeworkParser/src/bot-sync.js:224).

Уведомления включают полное описание, а транспорт отвергает сообщение длиннее 4096 символов. Разбиения или сокращения нет. После ошибки цикл источника прерывается, и та же ошибка повторится в следующем цикле.

Воспроизведение: задание с описанием в 5000 символов перед обычным заданием дало **0 отправок** и только **1 сохранённую запись**. Ограничение 50 символов применяется к спискам и эту проблему не решает.

Исправление: согласовать сокращение со ссылкой на оригинал либо безопасное разбиение уведомлений с сохранением кнопки; отдельная неисправимая отправка не должна блокировать остальные.

### 8. [P2] Ошибка логина E-school блокирует весь запуск

Место: [bot-cli.js:38](/C:/projects/HomeworkParser/src/bot-cli.js:38); аналогично [sync-cli.js:17](/C:/projects/HomeworkParser/src/sync-cli.js:17).

Основание: прямой анализ control flow; реальный логин не запускался.

Исправление: перенести первоначальную авторизацию в защищённый цикл E-school и запускать Telegram UI независимо. Добавить тест entrypoint, где E-school недоступна, а Classroom работает.

### 9. [P2] Classroom не обеспечивает полноту и устойчивое восстановление

Места: [classroom-web.js:12](/C:/projects/HomeworkParser/src/classroom-web.js:12), [classroom-web.js:2115](/C:/projects/HomeworkParser/src/classroom-web.js:2115), [classroom-web.js:2179](/C:/projects/HomeworkParser/src/classroom-web.js:2179), [ARCHITECTURE.md](/C:/projects/HomeworkParser/docs/ARCHITECTURE.md).

Архитектура прямо фиксирует, что `/a/not-turned-in/all` возвращает определённую выборку; ранее при сравнении с UI было найдено задание вне этой выборки. Пагинация реализована, но не доказывает полноту всех опубликованных заданий. Текущий аудит не повторял тот live-эксперимент и не выдаёт его за новое измерение.

`at`, `f.sid`, `bl` извлекаются динамически, но страницы и bootstrap кэшируются на весь процесс. В production-пути нет сброса кэша или bounded refresh при отказе RPC; следующий цикл использует те же значения. ## Что уже сделано хорошо

- В worker нет публичного HTTP endpoint. Запросы приложения направлены в ожидаемые E-school, Google и Telegram endpoints; скрытой сторонней отправки секретов в проверенных исходниках не найдено.
- Telegram команды и callbacks проверяют настроенный chat id. Для групп это доступ на уровне всей группы, не отдельного участника.
- SQL использует prepared statements с параметрами. Тесты реально открывают SQLite, проверяют повторное открытие, migration и сохранение статусов.
- Успех доставки записывается только после успешного Bot API; базовый повтор при ошибке покрыт тестом. Ограничения очереди описаны в пункте 4.
- HTML-текст и ссылки экранируются; опасные схемы URL и embedded credentials отбрасываются.
- Обычные network-ошибки Telegram скрывают URL с bot token. Для cookies остаются подтверждённые исключения из пункта 2.
- Основные приватные файлы перечислены в `.gitignore`; OAuth token сохраняется атомарно с mode 0600.
- В Render предусмотрены worker, `npm ci --omit=dev`, секреты без значений в YAML и `/var/data/homeworks.sqlite` на Persistent Disk.

## Условия готовности к Render

1. Исправить пункты 1–4 и добавить регрессионные сценарии; устранить проблемы 5–8 до обещания надёжной работы 24/7.
2. Проверить сборку и тесты на выбранной целевой Node.js. В текущем Blueprint buildCommand тесты не запускает; автоматической проверки в CI в этой копии не обнаружено.
3. Подключать **один Background Worker** с постоянным диском; перед переключением выключить локальный polling тем же токеном. Worker и диск соответствуют подходящему типу размещения; диск необходим, поскольку прочая файловая система эфемерна. [Render workers](https://render.com/docs/background-workers), [Render disks](https://render.com/docs/disks).
4. Продумать остановку: bot ждёт весь активный sync, но несколько последовательных запросов могут занять больше стандартного окна Render в 30 секунд. `maxShutdownDelaySeconds` сейчас отсутствует. Нужны согласованный deadline и безопасное прерывание/возобновление; просто увеличение задержки не исправляет зависшее чтение тела. [Render graceful shutdown](https://render.com/docs/deploys#graceful-shutdown).
5. Проверить фактический Git snapshot перед публикацией; `.env`, credentials, cookies, SQLite и debug artifacts не должны входить в него. Не загружать всю локальную папку архивом как есть.
6. При необходимости сохранить текущие отметки выполнения и offset заранее согласовать перенос SQLite. Новая пустая БД на Render создаст собственный baseline, а локальные статусы автоматически не переносятся. Нужен проверенный способ резервного копирования и восстановления.
7. После исправлений провести согласованную live-проверку авторизации обоих источников, полноты Classroom, одной доставки и сохранности состояния после рестарта. Аудит не включает такой деплой и не подтверждает работоспособность cookies с IP Render.
